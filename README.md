# CookBook AI — кулінарний помічник

Навчальний MVP з дисципліни «Проєктний практикум». Додаток зберігає продукти
користувача та підбирає опубліковані рецепти, для яких є щонайменше 70% обов'язкових
інгредієнтів. Необов'язкові спеції не впливають на відсоток. Кількість продуктів
поки не враховується. Gemini-помічник враховує актуальний холодильник і побажання користувача.

Репозиторій: https://github.com/SemiTail/CookBook-AI

Стек: React 19, TypeScript, Vite, NestJS, Prisma 7, SQLite, Argon2, JWT.
Нові інгредієнти можна створювати кнопкою «+ Новий інгредієнт» у холодильнику або формі рецепта. Назва та категорія зберігаються у спільному каталозі; холодильники й власні рецепти залишаються персональними. Доступні 17 категорій, зокрема спеції, бобові, овочі, фрукти та ягоди. У холодильнику є теги, фільтр «Тип продуктів» і сортування за назвою або категорією. Вибір усіх при активному фільтрі охоплює лише видимі продукти. API: `GET /api/v1/ingredients/categories`, `POST /api/v1/ingredients` (JWT, поля `name`, `category`).
Хмарне демо ще не налаштоване. ПІБ і ролі учасників потрібно додати перед здачею.

## Запуск на цьому комп'ютері

У PowerShell з кореня проєкту:

```powershell
cd C:\Users\Monya\CookBook_AI
npm.cmd start
```

Команда збирає обидві частини, генерує Prisma-клієнт і запускає API та інтерфейс.
У Windows також можна відкрити `start.bat`: він виконує той самий запуск в одному вікні та показує помилки підготовки.
Відкрий http://127.0.0.1:5173. Для зупинки натисни Ctrl+C.
Перед цим зупини старі екземпляри серверів на портах 3001 і 5173.
Наявна база `backend/dev.db` зберігається; запуск не виконує reset або seed.

## Встановлення з нуля

Потрібні Node.js 22.12+ та npm; перевірено на Node.js 26.13.0 у Windows.
SQLite не потребує окремого сервера. Для нативних залежностей за відсутності
готових бінарних файлів можуть знадобитися засоби збирання C++.

```powershell
git clone https://github.com/SemiTail/CookBook-AI.git
cd CookBook-AI
npm.cmd --prefix backend ci
npm.cmd --prefix frontend ci
Copy-Item backend/.env.example backend/.env
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Встав згенерований секрет у `JWT_SECRET` у `backend/.env`.
Не копіюй шаблон поверх свого наявного `.env`.

```powershell
npm.cmd --prefix backend run db:migrate
npm.cmd --prefix backend run prisma:generate
npm.cmd --prefix backend run db:seed
npm.cmd start
```

Seed додає 2 демоакаунти, 34 інгредієнти та 10 рецептів. Нові випадкові паролі
показуються лише під час створення демоакаунтів. Можна просто зареєструвати власний
акаунт. Повторний seed оновлює демонстраційні рецепти; для наявної бази він необов'язковий.

## Посібник користувача

1. Відкрий `/register`, введи ім'я, email, пароль від 8 символів і підтвердження пароля.
2. Після реєстрації відкриється `/dashboard` з ім'ям та email із API.
3. У «Мій холодильник» обери продукт і натисни «Додати».
4. Розділ «Можна приготувати» оновиться після зміни холодильника.
5. Відкрий картку рецепта: інгредієнти, інструкція, час і КБЖУ на порцію.
6. Видали продукт кнопкою ×. Натисни «Вийти», щоб завершити сеанс.

### Власні рецепти

У розділі «Мої рецепти» натисни «Створити рецепт». Заповни назву, емодзі,
опис, час, порції, складність, інгредієнти й кроки приготування. Можна вибрати
емодзі з палітри або вставити власний. Емодзі зберігається в БД разом із рецептом;
картки більше не визначають його за назвою страви.

Нові рецепти за замовчуванням приватні та прив'язані до авторизованого користувача. На сторінці
власного рецепта доступні «Редагувати рецепт» і «Видалити рецепт» з підтвердженням.
Інші користувачі не можуть переглядати або змінювати приватний рецепт, навіть
за прямим посиланням. Наявні опубліковані демонстраційні рецепти залишаються
у спільному каталозі. Рекомендації враховують спільні та власні рецепти.
Калорійність, білки, жири та вуглеводи задаються **на одну порцію** у формі
створення та редагування. Кнопка «Розрахувати КБЖВ з інгредієнтів» використовує
довідкові значення на 100 г, масу кожного інгредієнта у г/кг і кількість порцій.
Якщо даних немає або використані штуки/мілілітри, форма пояснює, чого бракує;
значення можна ввести вручну. Розрахунок орієнтовний і включає всі додані інгредієнти.
Після зміни маси або кількості порцій натисни кнопку повторно.
Порожнє поле означає «невідомо» (показується «—»),
нуль зберігається як 0. Дозволено до 2 знаків після коми, від'ємні значення відхиляються.

### Фото й офіційні рецепти модератора

У полі «Фото страви (URL)» вкажи пряме http/https-посилання на зображення.
Фото показується в каталозі та на сторінці рецепта; якщо воно недоступне, показується емодзі.
Власне фото можна завантажити з комп'ютера (JPG, PNG або WebP до 2,5 МБ). Рецепти без фото відображають емодзі.

Модератор бачить прапорець «Опублікувати офіційний рецепт». Фото необов'язкове, достатньо емодзі.
Опублікований рецепт доступний усім у каталозі й підборі; зняття прапорця робить його приватним.
Редагувати й видаляти рецепт може його автор. Сервер перевіряє актуальну роль у БД:
звичайний користувач не може опублікувати рецепт або призначити собі роль через API.

Після реєстрації потрібного акаунта адміністратор на комп'ютері із сервером виконує:

```powershell
npm.cmd --prefix backend run user:role -- email@example.com MODERATOR
```

Заміни email на адресу потрібного акаунта, потім вийди й увійди знову.
Для відкликання ролі використай `USER` замість `MODERATOR`.
Команда не створює акаунти і не змінює паролі. У цій перевірці роль особистим акаунтам не призначалася.

Після оновлення існуючої копії: `npm.cmd --prefix backend run db:migrate`,
потім перезапусти backend. Міграція додає поле `emoji` та емодзі деморецептів,
зберігаючи решту даних.

### Темна тема, холодильник і Gemini

- Кнопка сонця/місяця в шапці перемикає тему. Вибір зберігається у localStorage;
  при першому відкритті використовується тема операційної системи.
- «Обрати кілька продуктів» відкриває пошук і прапорці для масового додавання.
  Прапорці біля наявних продуктів дозволяють видалити обрані. «Очистити холодильник»
  видаляє лише ваші продукти після підтвердження.
- «ШІ-помічник» відкриває Gemini-чат. На широкому екрані це окрема колонка поруч
  із холодильником і рецептами; на вузькому — висувна панель. Чат можна згорнути,
  закрити та знову відкрити. Закриття не видаляє історію.
- Історія зберігається у SQLite окремо для користувача 30 днів від кожної відповіді.
  Прострочені записи видаляються під час запуску, кожну годину та при роботі з чатом.
  Після простою сервера очищення відбудеться під час наступного запуску.
  «Очистити історію» видаляє її відразу після підтвердження.
- Gemini отримує запит, до 12 останніх пар повідомлень, актуальний холодильник
  і до 40 доступних рецептів (спільні або ваші). Чужі приватні рецепти, email,
  паролі та токени не надсилаються. Відповідь ШІ сама не зберігає новий рецепт.

Ключ зберігається **лише у `backend/.env`**:

```env
GEMINI_API_KEY=ваш_ключ_Google_AI_Studio
GEMINI_MODEL=gemini-3.5-flash
```

Після зміни ключа перезапусти backend. Не додавай його до frontend або Git.
Міграція `20261110170000_chat_history` створює таблицю ChatTurn; застосування:
`npm.cmd --prefix backend run db:migrate`.
Використано [Gemini generateContent REST API](https://ai.google.dev/api/generate-content)
та [модель Gemini 3.5 Flash](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash).

## API та архітектура

Браузер → React → Vite proxy `/api` → NestJS `/api/v1` → Prisma → SQLite.
У production потрібен аналогічний reverse proxy або `VITE_API_URL` під час збірки.

| Метод | Шлях після `/api/v1` | Доступ |
|---|---|---|
| GET | `/health` | Публічний |
| POST | `/auth/register` | Публічний, 201 |
| POST | `/auth/login` | Публічний, 200 |
| GET | `/users/me` | Bearer JWT |
| GET | `/ingredients`, `/recipes` | Публічний каталог |
| GET | `/recipes/mine` | JWT, лише власні рецепти |
| GET | `/recipes/:id` | JWT, спільний або власний рецепт |
| POST | `/recipes` | JWT, приватний рецепт; модератор може передати `isPublished: true` і `imageUrl` |
| PUT, DELETE | `/recipes/:id` | JWT, лише власник |
| GET, POST | `/fridge` | Bearer JWT |
| DELETE | `/fridge/:id` | JWT, лише власний продукт |
| POST | `/fridge/bulk` | JWT; `{ ingredientIds: UUID[] }`, до 200 |
| DELETE | `/fridge/selected` | JWT; `{ ids: UUID[] }`, лише власні записи |
| DELETE | `/fridge` | JWT; очистити власний холодильник |
| GET | `/recommendations` | Bearer JWT |
| GET, DELETE | `/assistant/history` | JWT; власна історія чату |
| POST | `/assistant/messages` | JWT; `{ message: string }`, до 4000 символів |

Приклад тіла реєстрації:
`{"name":"Олена","email":"olena@example.com","password":"Example-password-2026"}`.
POST холодильника: `{"ingredientId":"UUID з /ingredients","quantity":200,"unit":"г"}`.
Повторне додавання оновлює кількість, а не створює дублікат.
Помилки: 400 — невалідні поля, 401 — авторизація, 404 — не знайдено,
409 — email зайнятий. Паролі зберігаються як Argon2-хеші; JWT діє 2 години.
SPA зберігає JWT у sessionStorage, вихід очищує його в поточній вкладці.

## Тести

```powershell
npm.cmd test
npm.cmd run test:coverage
npm.cmd --prefix backend run db:status
```

Unit-тести перевіряють точний поріг 70%, порожні дані, необов'язкові інгредієнти,
дублікати та невалідні дані. Coverage стосується лише модуля `match.ts`.
HTTP-тести створюють ізольовану тимчасову SQLite-базу з міграції, запускають API
на вільному порту та перевіряють авторизацію, валідацію, CORS, холодильник,
приватні рецепти, права модератора, фото та підбір на 1000 синтетичних рецептах.
`npm test` також запускає тести розрахунку КБЖВ у frontend.
Особисту базу вони не змінюють.

Браузерна перевірка: `node scripts/browser-smoke.cjs` (потрібні Playwright та Edge;
для зовнішньої інсталяції Playwright задай `PLAYWRIGHT_MODULE`). Вона працює
на тимчасовій копії SQLite, перевіряє також мобільну верстку й зберігає
технічні результати у `tmp/browser-smoke/`.

Gemini в автоматизованих HTTP/браузерних тестах підмінено тільки через тестовий
preload-файл. Production використовує реальний REST API. Окрема явна команда
`node scripts/gemini-live-smoke.cjs` робить один платний/квотований запит із
синтетичним холодильником у тимчасовій БД. Результат останньої живої перевірки:
`docs/evidence/gemini-live-smoke.json`.

## Розгортання

1. На сервері встанови залежності через `npm ci` у backend і frontend.
2. Задай `DATABASE_URL=file:/absolute/persistent/path/cookbook.db`, випадковий
   `JWT_SECRET`, `HOST=0.0.0.0`, `PORT` та `FRONTEND_ORIGIN=https://адреса-фронтенду`.
3. Запусти `npm run db:migrate`, `npm run build`, `npm start` у backend.
4. Для окремого фронтенд-хостингу задай `VITE_API_URL=https://адреса-api/api/v1`
   перед `npm run build` у frontend та опублікуй `frontend/dist`.
   Налаштуй fallback маршрутів SPA на `/index.html`.
5. Обидва публічні сервіси мають використовувати HTTPS. SQLite-файл повинен
   лежати на постійному диску; потрібні резервні копії. Не розміщуй його на
   ефемерному filesystem serverless-функцій. Запускай один екземпляр API.
6. Виконай smoke-сценарії з `docs/practical-work.md` на публічному URL.

## Виправлення `Failed to fetch`

У `start.bat` виправлено виклик неіснуючого backend-скрипта `dev`.
Тепер launcher викликає кореневий `npm start`, збирає застосунок і запускає
обидва сервери разом; помилка запуску залишається видимою в консолі.
Додано підтвердження пароля, перевірку відповіді входу та очищення сесії
при 401 із захищених маршрутів, зокрема сторінок рецепта.

Підтверджена причина: `importFileExtension = "ts"` у генераторі Prisma залишав
імпорти `.ts` у JavaScript-збірці, і API падав з `Cannot find module './internal/class.ts'`.
Тепер генератор має `moduleFormat = "cjs"`, `importFileExtension = "js"`, а збірка
автоматично запускає генерацію. Додано локальний API-проксі та повідомлення про
недоступність сервера. Перевірка API: http://127.0.0.1:3001/api/v1/health.

Якщо порт зайнятий — зупини попередній сервер. Якщо секрет відсутній — налаштуй
`.env`. Якщо таблиць немає — виконай `db:migrate`; не запускай `migrate reset`.

## Спільнота, профілі та Markdown
- Рецепти мають вкладки: свої, офіційні, що можна приготувати, браузер спільноти.
- Прапорець «Показувати в браузері рецептів спільноти» відкриває рецепт іншим. За замовчуванням він вимкнений. Зняття прапорця знову закриває доступ, якщо рецепт не офіційний.
- У «Мій профіль» можна змінити ім’я, аватар і обкладинку за URL, опис Markdown та дозвіл показу вітрини. Вітрина показує лише оприлюднені рецепти, ніколи приватні. Email не публікується.
- На сторінці рецепта є оцінки 1–5, коментарі з переходом до профілю автора та продукти, яких немає у холодильнику. Повторна оцінка змінює попередню; коментар може видалити лише його автор.
- Описи й інструкції підтримують CommonMark/GFM: таблиці, заголовки, списки завдань, цитати, код, посилання та зображення; є панель форматування й попередній перегляд. Сирий HTML не виконується.
- Категорії створюються у формі нового інгредієнта. Емодзі необов’язковий. Холодильник використовує мультивибір із пошуком та фільтром категорій.
- Міграція: npm.cmd --prefix backend run db:migrate. Після оновлення перезапустіть обидва сервери.

## Модерація каталогу й авторства
Створення категорій і продуктів доступне лише модераторам (обмеження перевіряється сервером).
Вибір продуктів у холодильнику й редакторі використовує спільний IngredientSelection.
Модератор може увімкнути «Показати також уже додані», щоб видаляти і використані продукти.
Після підтвердження видалення продукт забирається з усіх холодильників, покупок і рецептів; самі рецепти залишаються, КБЖВ очищуються.
Модератор може вибрати нового автора під час редагування. Першочерговий автор зберігається окремо й незмінно; він доступний лише модераторам у деталях рецепта та редакторі.

## Власні фото страв
Фото необов’язкове, зокрема для офіційних рецептів: без нього використовується емодзі.
У редакторі можна завантажити JPG/PNG/WebP до 2,5 МБ (2 500 000 байтів) або вказати зовнішнє посилання.
Сервер перевіряє зображення, зменшує великі фото до 2048 px і зберігає WebP у SQLite.
Завантажене фото можна прибрати або замінити. Резервна копія SQLite містить також ці фото.
## Джерела КБЖВ каталогу
Імпорт USDA SR Legacy 2018: https://fdc.nal.usda.gov/download-datasets/ (CC0).
Значення наведені на 100 г їстівної частини. Вуглеводи USDA за різницею включають клітковину.
Статус verified означає прямий відповідник назви у довіднику, а не лабораторне вимірювання конкретної покупки.
Для неоднозначних або непідтверджених назв використовується needs_review; наближені аналоги не імпортуються.
Нехарчові аксесуари not_food не входять у розрахунок поживності. Старі непідтверджені числа не використовуються автоматично.
Зіставлення й джерела: scripts/nutrition/catalog.json. Невирішені позиції: scripts/nutrition/review-needed.json.
Імпорт за замовчуванням показує dry-run: python scripts/nutrition/import_catalog.py; --apply створює резервну копію і застосовує транзакцію.

## Кілька категорій, регіони та діапазони
В меню продуктів відкрийте «Категорії та регіони»: можна вибрати кілька пунктів за алфавітом або перейти до регіонів світу. Усередині одного фільтра діє «або», між категоріями й регіонами — «і».
Регіони — редакційні кулінарні асоціації, не довідка про географічне походження конкретної покупки. Універсальні продукти мають окрему групу.
КБЖВ сортуються на 100 г, у двох напрямах. Для потребуючих уточнення продуктів відображається мінімум–максимум існуючих варіантів USDA, а за відсутності сімейства — явно позначений широкий діапазон категорії.
Такі діапазони не є лабораторними межами чи точними значеннями конкретного продукту. Для сортування використовується середина інтервалу; розрахунок поживності рецепта продовжує вимагати уточнення.
Реальні значення не перезаписуються діапазонами. Повторна побудова тегів та діапазонів: python scripts/nutrition/enrich_catalog.py (автоматична резервна копія).
